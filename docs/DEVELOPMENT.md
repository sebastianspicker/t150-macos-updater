# Development

## Layout

```text
Sources/T150Core/      firmware catalog, PE overlay reader, cabinet import, decoder, private files
Sources/T150Updater/   SwiftUI app and the client that runs the bundled tools
Native/                C USB engine (t150_engine.c plus policy, transport, device, storage)
script/                build, package, audit and icon scripts
Resources/             app icon (generated by script/make_icon.sh)
.github/               CI workflow, issue and pull request templates
docs/                  user and developer documentation
```

The app only launches its own bundled tools by absolute path, never anything from
`PATH`.

## How the pieces fit

The importer treats the installer as data. A pinned SHA-256 of the whole file
admits a known package before anything is parsed. The cabinet contents, the
driver, the wrapped TMF and the decoded TMF must all match the catalog. Vendor
code is never run.

The C engine pins the V35 payload and the V5 bootloader on its own, independent of
the Swift side. It builds the expected full image from the live backup plus the
selected target. An unfamiliar starting application never relaxes the bootloader
or flash geometry checks.

There is deliberately no downloadable profile, no free image selection, no
checksum override, no automatic acceptance of future installers, and no general
restore command. Supporting a new firmware needs a source change on both the Swift
and native side, a decoder check, a review of transport, geometry and recovery,
tests, and a new app release. A new version number alone is not enough.

### Target profiles

`Native/policy.inc` holds the compiled table of target profiles (`PROFILE_SLOTS`).
The engine builds every target itself from the hash-pinned official decoded image
plus an optional `BytePatch` table. The result must equal the profile's pinned
full-image SHA-256 and pass the footer and vector checks. `prepare` needs
`--profile NAME`, which only selects a compiled entry. `apply` and `finish` read
the profile from the session manifest (schema 2).

- **Upgrades:** from any structurally valid application older than the target.
- **Same version:** only from the pinned full-flash images in
  `same_version_baselines`, which are the other six V35 builds. Every pair is
  accepted in both directions. The self-test checks that each listed hash is
  another compiled profile of the same version. A wheel that already holds the
  exact target gets `already_current` after the two backups.
- **Patches:** each entry asserts its original bytes, stays inside `0x2000` to
  `0xfff7` (never the bootloader, version word or footer), changes at least one
  byte and is at most 8 bytes long. The engine recomputes the footer sum after
  patching.

| Slot | Profile | Entries | SHA-256 |
| --- | --- | --- | --- |
| 0 | `t150-v35-boot5` (official) | 0 | `37a48179…5056` |
| 1 | `t150-v35-fixes-boot5` | 26 | `7822b909…3f34` |
| 2 | `t150-v35-full-boot5` | 122 | `a4444a06…509b` |
| 3 | `t150-v35-sibrec-boot5` | 329 | `6874dd15…f9a9` |
| 4 | `t150-v35-sibrec-feat-boot5` | 368 | `e921b91e…6886` |
| 5 | `t150-v35-sibrec-raw-boot5` | 345 | `1e2de4a3…128a` |
| 6 | `t150-v35-sibrec-feat-raw-boot5` | 384 | `e934f1e6…2005` |

What each build changes is described in [FIRMWARE_BUILDS.md](FIRMWARE_BUILDS.md).
Each Swift `FirmwareTarget` also has a short `name`, a `tagline` and a `role`
for the build picker: `official`, `modified`, `recommendedFix` (exactly one) or
`extra` (shown collapsed). All seven set `allowsSameVersion: true`. Slots 2 to 6 also
set `requiresDoubleOptIn: true`, which the GUI turns into a second
acknowledgement.

The patch tables were generated and checked against stock V35 with
`script/fixes_profile.py MANIFEST STOCK --profile NAME [--array-only]`. The patch
manifests and the stock image are not part of this repository.
The maintainer's offline test suite, which is not part of this repository, checks
that the Swift catalog and the engine table agree. With real firmware fixtures it
also builds each pinned image from real bytes: from stock, from older versions and
from every other build. It checks reverts to stock and refuses a flipped byte in
the added code, a tampered footer and partial patch sets.

## Checks

On an Apple Silicon Mac with Swift 6 or newer and CMake 3.21 or newer:

```sh
./script/package_app.sh
./script/audit_bundle.sh
./script/build_and_run.sh --verify
```

`package_app.sh` builds Unshield, the engine and the app and then runs the bundle
audit, which includes the engine's built-in `self-test`. Neither sends USB
requests. CI (`.github/workflows/ci.yml`) runs `package_app.sh` on a GitHub
macOS 15 runner automatically for Dependabot-authored pull requests, or by
manual dispatch. The separate security workflow builds the same source for
CodeQL Swift/C analysis on its own triggers; neither workflow publishes a
release or updates a wheel. The test suite is kept private.

Launching the GUI is not an end-to-end test. Don't run `prepare`, `apply` or
`finish` against a wheel as a routine check.

`build_unshield.sh` downloads a SHA-256-pinned Unshield 1.6.2 source archive into
`.build`, builds a static libunshield with its own MD5 code and without OpenSSL,
and targets macOS 14. Only the extractor executable goes into the app, and it
links only macOS system libraries. Homebrew's `unshield` is not used, because it
may target a newer macOS. See [THIRD_PARTY.md](THIRD_PARTY.md).

The native build and the Swift package both target macOS 14. `audit_bundle.sh`
checks each executable's deployment target and library dependencies, the
required bundle paths, the plist, the ad-hoc signatures, that no proprietary file
types or developer paths are included, and the bundled tools' offline
self-tests. Packaging strips debug symbols before signing. The deployment target
check does not replace running the app on each macOS version.

`script/build_and_run.sh` packages and opens the app. It refuses to rebuild while the updater is
running and never kills an update. Other modes: `--debug`, `--logs`,
`--telemetry`, `--verify`.

## App icon

`script/make_icon.sh` compiles `script/make_icon.swift`, which draws the icon with
Core Graphics and writes `Resources/AppIcon.icns` and `Resources/AppIcon.png`.
Packaging copies the `.icns` into the bundle, and the bundle audit checks that it
is there. Run the script again after changing the drawing code.

## Bundle

```text
T150 Firmware Updater.app/Contents/
  Info.plist
  MacOS/T150Updater
  Resources/AppIcon.icns
  Resources/Tools/t150-engine
  Resources/Tools/unshield
  Resources/ThirdPartyNotices/
```

Packaging builds and checks the new bundle in a staging folder before it replaces
the local app. The previous app is kept as
`dist/T150 Firmware Updater.previous.app`. Packaging never kills a running
updater, so quit it normally first. Session data lives outside the bundle.

`ditto` creates the zip. Signing is ad-hoc, nested executables first. There is no
Developer ID signing, hardened-runtime check, notarization or upload. A public
release would need its own signing setup and credentials.

## Public repository boundary

Only the package, the native engine, synthetic tests, scripts, resources and
public documentation belong in Git. `.gitignore` treats every top-level path as
private unless it is on the allowlist. It excludes the private `delivery`,
`evidence`, `src` and `tools` folders, build output, Windows executables and
drivers, firmware, cabinets, raw captures and logs. Check the index before
publishing:

```sh
git diff --cached --check
git ls-files
git grep --cached -n -E '/Users/|/private/tmp/|BEGIN .*PRIVATE KEY'
```

A clean search is not proof that nothing private is left, so look at the
matches. Never commit vendor downloads, personal paths, session folders or
captures. The scripts never push or publish anything.
